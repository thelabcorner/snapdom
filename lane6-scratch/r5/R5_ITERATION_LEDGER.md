# R5 iteration ledger

## Campaign state

- Frozen baseline: official SnapDOM v3 release.
- Frontier parent: R2 + R3 + R4 hardened candidate.
- Exactness: required for style/serialization semantics.
- Practical wall-latency epsilon: 2% for the controlled local browser benchmark.
- Stability: CoV >= 15% blocks ordinary timing acceptance.
- Null control: byte-identical crossover CI must include zero.
- Experiment choice: adaptive sequential design; maximize information gain + likely frontier
  movement + search-space elimination per unit cost.
- Engineering candidates may be developed concurrently in isolated worktrees; performance
  measurements on this machine are serialized.

### R5-D1 adaptive-design closeout

The original eager index was rejected as the production policy even though it had very large
utility-scale wins. The adaptive experiments found two interaction terms that mattered:

1. **rule count × eligible element count**: tiny repeated captures can make eager indexing slower;
2. **keyed-rule density × total rule count**: an index cannot prune enough work when most rules
   are unkeyed.

The production candidate therefore behaves like a tiny tiered interpreter/JIT:

```text
linear R3 rule filter
  -> only consider JIT when keyed rules >= 64
  -> only when keyed rules are >= 1/3 of all candidate rules
  -> count key-prunable work inside THIS capture
  -> switch after >= max(2048, 4 * totalRuleCount) paid keyed checks
  -> compile subject buckets once for the style epoch, reuse structure later
  -> still re-earn the per-capture routing threshold before using it
```

That last condition is deliberate: the compiled program may persist, but a later tiny capture is
not forced onto the indexed interpreter merely because an earlier large capture paid to compile it.
