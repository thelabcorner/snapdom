### Scoped timing conclusion

For a repeat `cache:'soft'` capture of a large raster where scale/DPR changes invalidate the
compression memo, retaining the fetched Blob and sending it to the compression worker instead of
re-cloning/re-decoding the base64 data URL produces a **~56–57% reduction in snapDOM
capture/compression time** on this hosted Chromium workload.

This says nothing about cold captures, same-geometry repeats, small images, pages without a worker
route, or global snapDOM throughput.

## Native-memory evidence from run 1

Run 1 used **summed Chromium process-tree VmRSS**, not PSS. Treat these values as diagnostics, not a
final memory policy.

Primary post-warm retention delta (candidate minus baseline):

- large-scale: **+130 KiB**, 95% CI **[-1593, +1853] KiB**
- large-dpr: **+856 KiB**, 95% CI **[-211, +1923] KiB**
- large-same: **-826 KiB**, 95% CI **[-3271, +1619] KiB**
- small-scale: **+113 KiB**, 95% CI **[-781, +1008] KiB**
- large-csp: **-1114 KiB**, 95% CI **[-2182, -46] KiB**

The retained Blob therefore did **not** produce a resolved positive warm-retention penalty in this
experiment.

The post-warm unique-geometry sweep was dramatically different:

- large-scale: candidate minus baseline **-193190 KiB**
- large-dpr: candidate minus baseline **-192646 KiB**

Per runner, baseline grew roughly **276–281 MiB** during the geometry sweep while candidate grew
roughly **77–94 MiB**. Same-geometry, small and CSP controls did not reproduce that delta.

### Memory interpretation

The most plausible mechanism-consistent interpretation is avoided transient/retained pressure from
repeated multi-megabyte string structured-clones plus base64 decoding on the baseline worker path.
However, run 1 does **not** directly prove that explanation because:

1. the frozen baseline has no internal `__assetRoutes` counters, so its worker/string path was
   source-derived rather than independently instrumented in the page;
2. summed VmRSS double-counts shared mappings and is weaker than process-tree PSS;
3. no final acceptable retained-Blob cap was preregistered.

Accordingly, the 64 MiB `MAX_IMAGE_BLOB_BYTES` value remains **HYPOTHESIS**, not policy.

## Why confirmation v2 exists

The follow-up measurement harness must preserve the exact candidate mechanism while strengthening
measurement only:

1. instrument browser `Worker` construction/post/message/error for **both baseline and candidate**
   before bundle import;
2. prove the baseline claim arm actually posts to and receives from the worker, rather than silently
   falling back;
3. use a distinct width-change claim path instead of duplicating effective density with both
   scale and DPR;
4. make process-tree **PSS** from `smaps_rollup` the primary native-memory metric, retaining VmRSS
   and anon+shmem as diagnostics;
5. require stable `pid:starttime` process identity through the memory settle window;
6. report a runner-matched claim-minus-CSP retention difference-in-differences.

The original run remains valid for its exact estimand regardless of what confirmation v2 finds.
The confirmation run may strengthen, narrow or falsify the interpretation; it must not rewrite this
record.
